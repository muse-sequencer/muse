





## recursion issue - with midi event routing - SOLVED
### considerations: 
- there is a _possible_ but not yet seen recursion issue:
  if muse creates an midi-out-port for each jack input, 
  it has to re-create its ports if jack devices get connected/disconnected. 
  but this re-creation again changes jack-port graph, thus possible recursion. 
  
- related issue: with one (or more!) cross-over daemons (alsa-to-jack midi). 
  if the alsa graph changes, jack graph changes too. 
  again, a possible recursion issues, if muse connects to jack ports that  actually are alsa-derived.



## INSPECTION result 

I traced through the actual call chains to see whether it's a real risk here.

## Does MusE re-create ports on every graph change?

No — checked directly:
```
jack_port_register() is only called from:
  JackAudioDevice::registerInPort()/registerOutPort()  (jack.cpp:1381/1396)
    ← called only from MidiJackDevice::open()          (jackmidi.cpp:338/424)
      ← called only from createJackMidiDevice()/enumerateJackMidiDevicesImpl() (startup)
        and from explicit user action (toggling read/write on a midi port in the GUI)
```
`graphChanged()` → `processGraphChanges()` → `processJackCallbackEvents()` → `checkNewRouteConnections()` never call `registerInPort`/`registerOutPort`. They only call `jack_connect()`/`jack_disconnect()` and (now) `jack_port_set_alias()`. So the specific loop you're worried about — *graph change → create new port → graph change → create more ports* — doesn't exist in this codebase. Port creation happens exactly once per device, at startup or on explicit user toggle, never as a reaction to the graph itself changing.

## Why `jack_connect()`/alias calls in the callback path don't runaway

Two separate safety nets are already in place, independent of anything I added:

1. **Debounced dispatch**: the realtime JACK callback thread only sets `atomicGraphChangedPending` (jack.cpp) — the actual processing (`graphChanged()`) runs once, later, in the GUI thread. It's not "callback calls itself directly."
2. **Idempotency**: every `jack_connect()` call is guarded by `jack_port_connected_to()` — if the connection already exists, nothing happens. A second, third, Nth graph-changed event caused by MusE's own `jack_connect()` call will find "already connected" and stop there. Same logic applies to my `setMidiConnectionAlias()`: it's a no-op if the alias already matches, and — importantly — **setting/unsetting an alias doesn't fire any JACK callback at all** (no `PortRegister`/`PortConnect`/`GraphChanged` event is generated by `jack_port_set_alias()`), so it can't feed back into `graphChanged()` in the first place.

## The a2j/PipeWire cross-daemon case — this is the real one

This is legitimate and is exactly the mechanism behind the self-connection bug we already found: 
`ALSA graph changes → a2j/Midi-Bridge mirrors it into the JACK graph → JACK graph-changed fires → MusE reconnects a route to the (bridged) port`. 

If that bridged port happens to *be* MusE's own ALSA input, reconnecting to it doesn't just risk recursion — it's a direct self-loop (which is the bug you originally reported). The `isOwnBridgedMidiPort()` filter I added in `getJackPorts()`/`checkNewRouteConnections()` specifically cuts this path at its root: MusE will no longer discover or connect to its own bridged-back port in the first place, so there's nothing left to feed back into the ALSA graph on that side.

The remaining, weaker link: if MusE connects to *someone else's* legitimately bridged port (e.g. a hardware synth via a2j) and that changes the ALSA sequencer's subscription state, MusE's own `alsaProcessMidiInput()` (`alsamidi.cpp`) will see a `SND_SEQ_EVENT_PORT_SUBSCRIBED` and set `atomicAlsaMidiScanPending`, triggering one `alsaScanMidiPorts()` pass. That pass is also idempotent (it only subscribes if the device's address doesn't already match), so it self-terminates rather than looping — but it's the one part of this chain I haven't stress-tested against a real a2j+PipeWire-bridge combo, since I can't run JACK here.

## Recommendations

Nothing to change currently. 
The architecture is sound and the fix already closes the concrete loop path. 
If you want a cheap insurance policy for the theoretical case anyway (e.g. a bridge daemon behaving unexpectedly), I can add a lightweight **rate/depth guard** in `graphChanged()`: count re-entries within a short time window, and if it exceeds some threshold (say 20 in under a second), log a warning and skip processing once instead of hammering `jack_connect()`. Cheap, non-invasive, pure safety net.
